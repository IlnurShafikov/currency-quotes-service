# Design decisions

This document records the decisions behind the service: what was chosen, why,
what else was considered and what the choice costs. The README lists the most
important ones; this is the full list.

Every entry has the same four parts, so the document can be scanned rather
than read from top to bottom.

## Data model

### A quote and an update request are stored separately

**Decision.** `quotes` holds prices; `quote_update_requests` holds requests.
A completed request references the quote it produced.
**Why.** They are different things. A quote is an immutable fact: a price at
a point in time. A request is a process with a lifecycle.
**Alternatives.** One table with a nullable price. Every unfinished request
would carry an empty price, and "the latest quote" would need a status filter.
**Trade-off.** Reading a completed update takes two queries instead of one.

### The requests table is the job queue

**Decision.** The background worker takes its work from
`quote_update_requests`; there is no separate queue.
**Why.** The request and the job are the same row, written by one `INSERT`,
so a request can never be accepted without being queued. Pending work
survives restarts and is shared by all instances.
**Alternatives.** A Go channel loses accepted requests when the process dies
and does not work across instances. A message broker needs an outbox to give
the same guarantee and adds infrastructure.
**Trade-off.** The queue is limited by what PostgreSQL can handle, which is
far beyond the needs of this service.

### The database enforces the rules of the domain

**Decision.** `CHECK` constraints forbid impossible states: a completed
request without a quote, a failed one without a reason, a pending one with a
finish time, a pair of identical currencies, a non-positive price. The
constraints have explicit names.
**Why.** The domain checks the same rules, but the database is the last line
of defence against a bug in the adapter or a manual change. A named
constraint makes a violation readable in the logs.
**Alternatives.** Rely on the application alone.
**Trade-off.** The rules exist in two places and must be changed together.

### Status is text with a check, not an enum type

**Decision.** `status` is `TEXT` with `CHECK (status IN (...))`.
**Why.** Changing the allowed values is an ordinary migration. A PostgreSQL
`ENUM` cannot drop a value, and adding one has restrictions inside a
transaction.
**Alternatives.** A native `ENUM` type.
**Trade-off.** A few more bytes per row.

### A currency is identified by its code

**Decision.** The primary key of `currencies` is the code itself, stored as
`VARCHAR(10)`; other tables reference it directly.
**Why.** The code is unique and stable by nature, and rows that reference it
are readable without a join.
**Alternatives.** A numeric surrogate key, which would add a join to every
read. `CHAR(3)`, which would fit ISO 4217 exactly but would have to be widened
on a populated table to support any other asset.
**Trade-off.** The column is wider than the current validation needs.

### Prices are decimals everywhere

**Decision.** A price is `decimal.Decimal` in Go, `NUMERIC(38, 18)` in
PostgreSQL and a string in JSON. The provider response is decoded straight
into a decimal. On reads, `trim_scale` removes the zero padding of the column.
**Why.** Binary floating point cannot represent most decimal fractions
exactly. A string in JSON keeps clients from parsing the price as a float.
**Alternatives.** `float64`, or an integer number of minor units. The latter
does not suit exchange rates, which have no fixed number of fraction digits.
**Trade-off.** Clients must convert the string themselves.

### Identifiers are UUIDv7 generated by the application

**Decision.** Update and quote identifiers are UUIDv7, created before the row
is written. `UpdateID` and `QuoteID` are distinct Go types.
**Why.** The handler knows the identifier without asking the database.
UUIDv7 is ordered by time, so new rows go to the end of the index, and it
does not reveal how many requests exist. Distinct types make it a compile
error to pass one kind of identifier as the other.
**Alternatives.** `BIGSERIAL` exposes volume and ties identity to the
database. UUIDv4 is random and fragments the index.
**Trade-off.** 16 bytes per key instead of 8.

## Requesting an update

### The handler does not perform the update

**Decision.** `POST /api/v1/quotes/updates` stores a pending request and
answers `202 Accepted` with its identifier and a `Location` header.
**Why.** The assignment requires the update to happen in the background.
`202` means exactly "accepted, not done yet".
**Alternatives.** None that satisfies the requirement.
**Trade-off.** A client needs a second request to get the price.

### Requests are deduplicated only while one is pending

**Decision.** While a request for a pair is pending, further requests for
that pair return its identifier. Once it is finished, the next request
creates a new update.
**Why.** A quote does not belong to a client: everyone asking for EUR/MXN
wants the same thing, and one provider call answers them all. This also
protects the provider from bursts.
**Alternatives.** A client-supplied `Idempotency-Key` returns the same result
even after completion, but needs key storage and expiry and puts the burden
on clients. A time window ("at most once per N seconds") is throttling, not
idempotency, and would return a stale price to someone who asked for a fresh
one.
**Trade-off.** This is deduplication of in-flight requests, not idempotency
in the strict sense: a retry after completion starts a new update. For a
"refresh" operation that is harmless.

### One statement makes the deduplication atomic

**Decision.** The request is stored with
`INSERT ... ON CONFLICT (...) WHERE status = 'pending' DO UPDATE ... RETURNING`
against a partial unique index. The `DO UPDATE` assigns a column to itself.
**Why.** The statement returns either the new row or the existing one, with
no window between checking and inserting. `DO NOTHING` would return no row on
a conflict and require a second query, which can race with a worker finishing
the request.
**Alternatives.** `SELECT` then `INSERT` in application code: two concurrent
requests both find nothing and both insert.
**Trade-off.** Each duplicate request writes a new version of the row.

### Currencies are validated twice

**Decision.** The domain accepts a code only if it is a known ISO 4217
currency. The service then checks the `currencies` table to see whether the
currency is supported.
**Why.** The two checks answer different questions, and the client gets
different errors: `invalid_currency` for a typo, `unsupported_currency` for a
real currency the service does not handle. The table is the single source of
truth for what is supported and is changed by a migration, not a release.
**Alternatives.** Only the table: a typo would be reported as "not
supported". Only a list in the configuration: no referential integrity.
**Trade-off.** One extra query per request, including reads.

## Background processing

### The worker polls the database

**Decision.** The worker asks for pending requests every `WORKER_INTERVAL`
and keeps processing batch after batch until none is left.
**Why.** Polling works the same for one instance and for ten, and needs no
state outside the database.
**Alternatives.** An in-process channel would start processing instantly but
only within one process, and polling would still be needed as a fallback.
PostgreSQL `LISTEN/NOTIFY` is a possible optimisation on top of polling.
**Trade-off.** Up to one interval of latency before processing starts, and
one cheap query per interval when idle.

### A request is claimed before it is processed

**Decision.** `ClaimPending` marks requests as started in a single
`UPDATE ... WHERE id IN (SELECT ... FOR UPDATE SKIP LOCKED)`.
**Why.** Two workers never receive the same request, and neither waits for
the other: locked rows are skipped. The claim is committed immediately, so no
transaction stays open during the call to the provider.
**Alternatives.** Holding a row lock for the whole processing keeps a
transaction and a connection open for the duration of an HTTP call. A
separate `processing` status does the same job as the claim timestamp with
one more state to manage.
**Trade-off.** A claimed request has to be released by time, see below.

### A claim expires

**Decision.** A request claimed more than `WORKER_STALE_AFTER` ago may be
claimed again. The comparison uses the database clock.
**Why.** If a worker crashes, its requests are picked up by another one
without any recovery procedure. Using the database clock means instances on
different machines agree on what "stale" means even if their own clocks
differ.
**Alternatives.** A heartbeat that extends the claim is justified for jobs of
unpredictable length; here a job is one HTTP call with a known upper bound.
**Trade-off.** A crashed worker's requests wait for the expiry. The claim
time cannot be controlled from tests, which compare requests without it.

### A lost claim cannot overwrite a result

**Decision.** Every claim increments `attempts`. `Finish` updates the row only
if `attempts` still has the value the worker received; otherwise it changes
nothing and returns `ErrClaimLost`.
**Why.** A worker can stall past the expiry (a long GC pause, a slow commit)
while another one takes the request over. The counter acts as a fencing
token: the late worker's write does not match.
**Alternatives.** Trusting the timeouts alone. They make the situation
unlikely, not impossible.
**Trade-off.** In that rare case the provider is called twice for one request.

### An attempt is counted when it starts

**Decision.** `attempts` is incremented by the claim, not by the outcome. A
request whose counter already exceeds the limit is failed without calling the
provider.
**Why.** If a request crashes the worker every time, an attempt counted only
on completion would never be counted, and the request would be retried
forever.
**Alternatives.** Counting on completion.
**Trade-off.** An attempt interrupted by a deploy is spent too. The graceful
shutdown exists to make that rare.

### Only the processor retries

**Decision.** A failed attempt leaves the request pending; it is claimed
again after `WORKER_STALE_AFTER`. The provider client makes one request and
does not retry. After `WORKER_MAX_ATTEMPTS` the request becomes `failed`.
**Why.** One retry policy in one place. Retries inside the client as well
would multiply calls to the provider and could push a batch past its
deadline.
**Alternatives.** Exponential backoff with a "not before" column.
**Trade-off.** The delay between attempts is fixed.

### A batch is processed concurrently under one deadline

**Decision.** The requests of a batch run in parallel. The whole batch shares
a deadline, `WORKER_TIMEOUT`, counted from before the claim.
**Why.** All requests of a batch are claimed at the same moment, so they
share the same expiry. A per-request deadline would let the last one run past
it. The configuration enforces
`RATES_API_TIMEOUT < WORKER_TIMEOUT < WORKER_STALE_AFTER`, so a live worker
always gives up before its claim expires.
**Alternatives.** Sequential processing does not fit ten slow provider calls
into one deadline.
**Trade-off.** A batch issues up to `WORKER_BATCH_SIZE` provider calls at once.

### A quote and the completion of its request are one transaction

**Decision.** Saving the quote and marking the request completed are
committed together. A failure is a single write and needs no transaction.
**Why.** A completed request always has its quote, and a quote from a worker
that lost its claim is rolled back.
**Alternatives.** Two independent writes can leave a quote without a
completed request, or the reverse.
**Trade-off.** None worth noting.

### Quotes can be refreshed on a schedule

**Decision.** With `SCHEDULER_INTERVAL` set, a scheduler requests an update for
every supported pair whose latest quote is at least one interval old or
missing: once on start-up, then every interval. It is off by default.
**Why.** Without it the latest quote of a pair is as old as the last request
for it, and a freshly started service has no quotes at all. The scheduler is
a third driving adapter next to the HTTP handler and the worker: it calls one
service method and puts ordinary requests into the existing queue, so
idempotency, retries and claiming work unchanged. Checking freshness first
keeps several instances from repeating each other: an instance that finds a
quote already refreshed does nothing.
**Alternatives.** Refreshing every pair on every tick regardless of age, which
multiplies provider calls by the number of instances. Fetching rates directly
in the scheduler, which would duplicate what the worker does. A list of pairs
in the configuration instead of every pair of supported currencies.
**Trade-off.** Every ordered pair is refreshed, which grows quadratically with
the number of currencies. While the provider is down, each tick spends a full
set of attempts per pair.

### Shutdown lets a running batch finish

**Decision.** On `SIGTERM` the worker starts no new batch but lets the
current one run to completion, bounded by `WORKER_TIMEOUT`. The HTTP server
finishes in-flight requests. The database pool is closed last.
**Why.** Cancelling a batch in the middle of a provider call would waste an
attempt of every request in it on each deploy.
**Alternatives.** Cancelling everything immediately.
**Trade-off.** A shutdown can take up to `SHUTDOWN_TIMEOUT`.

## Code structure

### Hexagonal architecture with ports owned by their consumers

**Decision.** `domain` holds the model, `service` the use cases. The service
declares the interfaces it needs (storage, provider, clock, ids); adapters
implement them. The handler and the worker declare the interface they need
from the service.
**Why.** Dependencies point inwards, so the business logic can be tested
without a database or HTTP, and an adapter can be replaced without touching
it.
**Alternatives.** A layered design where the repository package defines its
own interface makes the business logic depend on the storage layer.
**Trade-off.** More packages and interfaces than a service of this size
strictly needs.

### The transaction travels in the context

**Decision.** `Transactor.WithinTx` puts the transaction into the
`context.Context`; repositories pick it up from there.
**Why.** The service decides what must be atomic without seeing a driver
type, and cannot forget to commit or roll back.
**Alternatives.** Passing a transaction object through every method leaks the
driver into the business logic.
**Trade-off.** The transaction is implicit: a repository call made with the
wrong context silently runs outside it. A test covers this for each
repository involved.

### Time and identifiers are behind ports

**Decision.** The service gets the current time and new identifiers through
the `Clock` and `IDGenerator` interfaces.
**Why.** They are the two sources of non-determinism in the business logic.
With them replaced, a test can state the complete expected result.
**Alternatives.** Calling `time.Now()` and generating ids in place, then
comparing "everything except the time and the id" in tests.
**Trade-off.** Two more dependencies to pass around.

### The service returns errors; adapters log them

**Decision.** `service` has no logger. The handler logs unexpected errors,
the worker logs processing errors.
**Why.** The application layer stays free of side effects, and tests assert
on errors with `errors.Is` instead of parsing log output.
**Alternatives.** Logging where the error occurs.
**Trade-off.** An error must carry enough context in its message, since it is
logged far from where it happened.

### No ORM, no web framework, no dependency injection framework

**Decision.** SQL is written by hand and run through pgx. Routing uses
`net/http`. Dependencies are wired by hand in `cmd/server`.
**Why.** The queries that matter are PostgreSQL-specific (partial index,
`ON CONFLICT`, `SKIP LOCKED`); an ORM would hide them, not remove them. The
standard router supports method and path patterns since Go 1.22. Thirty lines
of explicit wiring are checked by the compiler.
**Alternatives.** GORM, a third-party router, a DI container.
**Trade-off.** More code written by hand.

### Exported fields in domain types

**Decision.** `Quote` and `UpdateRequest` have exported fields. Constructors
validate input and methods guard state transitions.
**Why.** The repository can restore an object from a row with a plain struct
literal.
**Alternatives.** Private fields with getters and a restore function taking
nine parameters.
**Trade-off.** Code outside the domain can build an invalid object by
bypassing the constructor. In this codebase only the repository and tests
build these structs directly.

## API

### Errors have one shape and hide internal details

**Decision.** Every error is `{"error":{"code","message"}}`. Validation
errors echo the client's own input. Anything unexpected becomes a `500` with
a fixed message and is logged. A failed update shows a fixed message; the
real reason stays in the database.
**Why.** A client can branch on `code`. Internal details such as addresses
must not leak.
**Alternatives.** Returning the error text as is.
**Trade-off.** Diagnosing a failure requires access to logs or the database.

### All input errors are 400

**Decision.** Malformed bodies, invalid and unsupported currencies and
invalid identifiers all answer `400`; the `code` tells them apart.
**Why.** One status for "the request is wrong" keeps client logic simple.
**Alternatives.** `422` for well-formed but unacceptable values.
**Trade-off.** Less precise at the HTTP level.

### The path carries a version

**Decision.** Routes live under `/api/v1`.
**Why.** A published contract cannot be broken; a version leaves room for an
incompatible `v2` next to it.
**Alternatives.** No version until one is needed, which means introducing it
after clients already depend on unversioned paths.
**Trade-off.** Slightly longer URLs.

### The specification is written by hand and verified by tests

**Decision.** `api/openapi.yaml` is maintained manually. Every handler test
validates the actual response against it.
**Why.** A hand-written document can carry several examples per response and
explain behaviour such as idempotency. The contract tests stop it from
drifting: an undocumented operation, status or missing field fails the build.
**Alternatives.** Generating the document from annotations keeps schemas in
sync with structs, but statuses and paths are still written by hand.
**Trade-off.** The tests check responses against the document, not the
reverse: an operation that is documented but does not exist goes unnoticed.

## Testing

### Repository tests use a real database

**Decision.** `repository` is tested against PostgreSQL. Each test creates
its own schema, applies the migrations and drops the schema afterwards.
**Why.** This layer is SQL. Its correctness depends on indexes, locking and
type conversions that a mocked driver cannot show. A schema per test isolates
tests and lets them run in parallel.
**Alternatives.** Mocking the driver. Truncating tables between tests, which
forbids parallel runs. testcontainers, which adds dependencies and needs
Docker for every run.
**Trade-off.** These tests need a database and are skipped locally without
one.

### Stubs are written by hand

**Decision.** Ports are replaced in tests by small hand-written stubs that
return preset values and record calls.
**Why.** The interfaces are small. A stub is a few lines and readable without
knowing a mocking framework.
**Alternatives.** Generated mocks with expectations.
**Trade-off.** A stub has to be extended by hand when a port grows.

### Tests may not be skipped on CI

**Decision.** Without `TEST_DATABASE_URL` the integration and end-to-end tests
are skipped locally and fail on CI.
**Why.** A silent skip would keep CI green while nothing is tested.
**Alternatives.** Always requiring a database, which makes `go test ./...`
fail on a fresh checkout.
**Trade-off.** The behaviour depends on the `CI` variable.

### The race detector runs on CI

**Decision.** `go test -race` runs on every pull request.
**Why.** The service has concurrent code: parallel batch processing, the
worker, graceful shutdown.
**Alternatives.** Running it locally, which on Windows needs a C compiler.
**Trade-off.** A race is found after pushing, not before.

## Operations

### Configuration comes from the environment and is validated as a whole

**Decision.** Settings are read from environment variables with the standard
library. Every problem is reported at once, and the timeouts are checked
against each other at start-up.
**Why.** Environment variables are the standard for containers. A service
with inconsistent timeouts would work until two workers start taking
requests from each other; refusing to start is safer.
**Alternatives.** A configuration file or a configuration library.
**Trade-off.** No reloading without a restart.

### Migrations run on start-up under a lock

**Decision.** The service applies pending migrations when it starts, holding
a PostgreSQL advisory lock. Migration files are embedded into the binary.
**Why.** The project starts with one command and no manual steps. The lock
keeps instances that start together from migrating concurrently.
**Alternatives.** A separate migration step in the deployment pipeline, which
is the usual choice for production.
**Trade-off.** A bad migration stops the service from starting.

### The image contains only the binary

**Decision.** A multi-stage build produces a static binary that runs in a
distroless image as an unprivileged user.
**Why.** Less to download and less to attack: no shell, no package manager.
The image still has the CA certificates needed to reach the provider.
**Alternatives.** An Alpine image, a few megabytes larger but with a shell.
**Trade-off.** No shell inside the container for debugging, and no
container-level health check for the service.
